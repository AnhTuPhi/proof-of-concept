One JVM ingests live price ticks from two exchange WebSocket feeds, merges them reactively, and fans them out to thousands of browsers over Server-Sent Events — on a few dozen threads. This page explains the flow, the key tech, why it scales, and where it stops.

Binance tick Coinbase tick merged / shared fan-out to SSE

Read it left → right

  • Ingest. Each exchange service holds one non-blocking WebSocket on the Netty event loop and normalizes raw JSON into a PriceTick.
  • Hub. Ticks go into a Sinks.Many.multicast() with a bounded, drop-oldest buffer — one slow reader can't stall the rest.
  • Merge + share. Flux.merge(sources).share() makes a single hot stream all clients read from.
  • Fan-out. Each SSE client attaches a lazy filter → groupBy → sample pipeline, prepends a snapshot, and mixes in a heartbeat.

The invariants that make it cheap

  • 1 upstream WS per exchange — independent of client count.
  • 1 Netty event loop (≈ CPU cores) serves every socket read & write.
  • 0 extra threads per subscriber — operators are a lazy plan, not workers.
Net effect measured in the load test: 5000 SSE clients on ~30–40 threads, < 200 MB heap. Jump to the Scaling tab to play with the numbers.

The single goal “push prices to everyone” hides five distinct sub-problems. Each is a place a naive build quietly falls over — with the reactive primitive that solves it.

P1 Connection amplification

Hold thousands of idle, long-lived downstream connections at once. Thread-per-connection pins a thread each and caps out at a few hundred–thousand.

Solved by

Reactor Netty event loop. SSE responses are Flux<ServerSentEvent>; idle streams pin no thread.

NettySSE

P2 Source multiplexing (fan-in)

Merge N async upstreams with different protocols (Binance URL-subscribe vs Coinbase send-a-frame) into one normalized stream — no callback soup.

Solved by

Flux.merge(List<ExchangeStream>) behind one interface; each quirk stays inside its service.

Flux.mergeExchangeStream

P3 Upstream connection economy

5000 browsers must not become 5000 exchange sockets (rate-limited / bannable). Decouple upstream count from downstream count.

Solved by

Sinks.Many.multicast() hub + aggregator .share() → N clients, 1 WS per exchange.

Sinks.Manyshare()

P4 Backpressure & slow consumers

Upstream may fire 100 ticks/s. A slow client must not force unbounded buffering, and one stuck client must not stall the other 4999.

Solved by

onBackpressureBuffer(1024,false) (drop-oldest) + per-client groupBy(symbol).sample(1000/maxHz).

drop-oldestgroupBysample

P5 Cold-start & liveness

A mid-session joiner would see a blank UI; idle streams get killed by proxy idle-timeouts.

Solved by

Warm-up concat(snapshot, live) from a ConcurrentHashMap + 15s mergeWith(heartbeat).

snapshotconcatheartbeat

What we're protecting

  • Server threads — stay flat (tens) as connections grow (thousands).
  • Server heap — bounded buffers, no per-client unbounded queue.
  • Upstream sockets — a rate-limited external resource; exactly one per exchange.
  • Delivery isolation — one slow client never becomes another's latency.
  • First paint — a new client sees data immediately.

The data contract

A normalized record is the boundary that isolates exchange-specific JSON from the rest of the system.

record PriceTick(
  String  symbol,        // BTCUSDT
  double  price,
  double  changePercent, // 24h
  double  volume,        // 24h base
  String  source,        // binance | coinbase
  Instant timestamp)

Coinbase BTC-USD→BTCUSDT and change-from-open_24h are computed inside the Coinbase service, so nothing downstream sees vendor shapes.

Tech debt we knowingly accept

  • D1 Single-instance state — snapshot, sinks, counter all in-JVM. Biggest debt; breaks at ≥2 instances.
  • D2 Per-instance upstream WS — K pods → K sockets/exchange.
  • D3 Drop-oldest is lossy — fine for display, wrong for audit/OHLC.
  • D4 No persistence/replay — late joiner gets snapshot+live only.
  • D5 Per-service ObjectMapper + hand-rolled parse.
  • D6 Symbols hard-coded — redeploy to change coverage.
  • D7 No auth / entitlements / per-user caps.
  • D8 Isolation leans on bounded buffer, not true pull backpressure.
  • D9 Subscriber count is process-local AtomicLong.

D1, D2, D9 are exactly what the Scaling design resolves.

What breaks at N instances — and the fix

The single-instance design has no shared state. Scaling it out doesn't distribute load — it forks the system into N inconsistent copies. Toggle the design:

  • C1 3× upstream sockets per exchange → rate limits / bans.
  • C2 Divergent snapshots — clients disagree on first paint.
  • C3 Subscriber count is per-pod → dashboards under-report ×N.
  • C4 Reconnect roulette: a pod death re-lands clients on a different snapshot → visible jump.
  • Ingest tier owns the only upstream WS — run as a cluster singleton (Lease/StatefulSet + PDB).
  • Shared bus carries normalized ticks, partitioned by symbol (ordering); a Redis snapshot hash gives identical warm-start.
  • Edge tier is what you kubectl scale — reuse the same filter→groupBy→sample→concat→heartbeat pipeline verbatim.
  • Autoscale on active-connections custom metric, not CPU (idle SSE is cheap). LB idle-timeout > heartbeat.
