Scaling (k8s / VM)

The umbrella problem

Teams keep shipping Elasticsearch as if it were a search-flavored database. It isn't, and the failure modes are silent.

The three assets this suite protects
  1. Data correctness — Postgres ↔ ES agreement, no silent drift.
  2. Availability — reads and writes survive load, migrations, and failure.
  3. Search quality — the ordering is the product, not just the set.

db-to-es-sync-poc port 8101

Three sync strategies side-by-side. Two work. One is here to fail on purpose.

Hard problem

ES writes are not part of the DB transaction. Naive dual-write drifts silently forever the first time ES has a hiccup.

What we protect

Data correctness — every DB row eventually reflected in ES with the correct value, or drift is detectable and repairable within a bounded window.

The three strategies

version_type: external. 3. Debezium CDC → ES App Postgres WAL (logical) Debezium embedded Kafka ES → least app code; watch WAL slot fill.

Tech debt (see TECHNICAL.md)
Outbox poller has no leader election → race in multi-pod. Debezium runs embedded (Connect for prod). No dead-letter topic.

es-eventual-consistency-poc port 8110

The 1-second refresh window is what breaks "I just saved it, where is it?"

Hard problem

ES refreshes new segments every 1s by default. User writes → immediate read → nothing there for up to a second.

What we protect

Read-your-writes for user-facing single-doc writes, without wrecking bulk throughput.

Four modes, one endpoint

ModeWrite costRead freshnessRight when
default~5msracenever (the counter-example)
wait-forup to 1simmediatesingle user writes
force-refresh~50msimmediateNEVER in bulk paths
read-through~5msimmediate (via DB)client hints "just created"

Out-of-order writes

esClient.index(i -> i.index("products").id(id)
    .document(doc)
    .versionType(VersionType.External)
    .version(updatedAt.toEpochMilli()));

ES rejects any write whose version ≤ current. Kafka replays / rebalances no longer flip docs backwards.

es-shard-sizing-poc port 8111

Shard math. ILM rollover. Mapping-explosion guardrails.

Rules of thumb

  • 10-50 GB per shard. Smaller wastes overhead; larger slows queries.
  • ≤ 20 × heap_GB shards per node (primaries + replicas).
  • Don't over-shard small indexes.
  • Time-series → ILM rollover, not fixed count.

ILM in plain English

  • Hot: writes + recent reads. SSDs, replicas=1.
  • Warm: force-merged to 1 segment, replicas=0.
  • Delete: gone.

Honest caveats

es-faceted-search-poc port 8108

Multi-select sidebar filters that update counts correctly.

The trick
post_filter filters the hits *after* aggs run, so aggs see the full set. Per-facet filter aggs re-apply the selection to only the non-selected facets so their counts reflect "if I applied this".

Consistency-vs-latency tradeoff

PatternSync guaranteeExtra latency

Suite recommendation
Outbox + SKIP LOCKED for writes • refresh=wait_for + Redis freshness flag for user-facing reads • CDC only when the ops team is comfortable owning it.
