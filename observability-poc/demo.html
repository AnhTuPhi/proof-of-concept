The magic: the trace_id shown above is the same string in the trace tree, in every log line, and (as an exemplar) on the metric. That single shared key is what collapses three tools into one investigation.

The three pillars, and why one alone isn't enough

Each answers a different question. Correlation by trace_id is what makes them a system instead of three silos.

Metrics  “Is something wrong?”

Cheap, always-on, aggregatable numbers. Good for alerting and trends; can't tell you about one specific request.

  • Counters: orders_created_total, payment_charges_total
  • Histogram: payment_charge_duration_ms
  • Pushed every 10s → Collector → scraped by Prometheus on :8889
  • Exemplars link a spike back to a real trace_id

Traces  “Where in the path?”

A tree of spans reassembled from every service by W3C Trace Context propagation.

  • Auto spans for http/express; manual spans for business steps
  • traceparent header carries context across processes
  • Parallel fan-out shows payment vs inventory side-by-side
  • Errors set SpanStatusCode.ERROR + record the exception

Logs  “What exactly happened?”

Richest detail, historically the hardest to correlate. Fixed by auto-injecting the trace context.

  • Structured JSON via pino
  • instrumentation-pino stamps trace_id/span_id on every line
  • Shipped as OTLP log records → Loki (label-indexed, not full-text)
  • Grafana derived field turns trace_id into a link to the trace

🔗 The join key

Two things make correlation possible:

  • trace_id — per request, on all three signals
  • resource attributes — service.name, service.version, deployment.environment on every signal
  • Grafana pivots trace → logs → metrics using these shared tags
Remove the shared trace_id and the “single pane of glass” degrades back into three browser tabs and manual timestamp-matching.

What breaks when you run many replicas

Full treatment in CONSISTENCY.md. The short version:

SignalScales for free?What you must do
Traces✓ mostly Self-describing per request — Jaeger stitches by ID regardless of which pod/collector. Except tail-sampling: needs a loadbalancing exporter keyed on traceID so all spans of a trace reach one collector.
Metrics✗ no Counter resets on pod churn (use rate()); need Prometheus service discovery per collector pod; pick exactly one aggregation point; unique service.instance.id per replica.
Logs✓ mostly Independent records, correlate by trace_id. Guard label cardinality (no order_id as a label); scaled Loki needs shared ring + object storage + replication_factor ≥ 3.
Collector— Split the one container into a stateless agent tier (DaemonSet / systemd per node) + a stateful gateway pool (tail-sampling, fan-out).

K8s (scale pods / HPA)

  • Agent = DaemonSet (one per node, free)
  • Discovery via kubernetes_sd_configs
  • service.instance.id = pod name/UID
  • Graceful drain via preStop + grace period
  • Pods churn constantly → counter resets are the norm

VMs (scale instances / ASG)

  • Agent = collector as a systemd service on each VM image
  • Discovery wired to the ASG (DNS/Consul)
  • service.instance.id must be injected (hostname/instance-id)
  • Graceful drain via ASG lifecycle hook + SIGTERM flush
  • Less churn, but still use rate()
Two things must be engineered deliberately either way: (1) route a trace's spans to one collector so tail-sampling is correct, and (2) give every replica a stable unique service.instance.id and aggregate metrics with rate(), so churn reads as churn — not corruption.
