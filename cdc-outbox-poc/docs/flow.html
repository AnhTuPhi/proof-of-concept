The three components, side by side

Hard problem

Two writes (business row + outbox row) must be one commit or no commits. The producer must not depend on Kafka being up. Cleanup DELETEs must not become downstream events.

What we protect
  • No order without its event, no event without its order
  • The wire contract: aggregate_id, headers, payload shape
  • The DB — never Kafka — is the source of truth
Solution shape

@Transactional service inserts both rows via JPA. No KafkaTemplate in this JVM. Scheduled cleanup deletes rows older than the retention window; connector filters the DELETEs from Kafka.

Key tech
  • OrderService · @Transactional
  • OutboxEventPublisher · DB-only insert
  • outbox_events · REPLICA IDENTITY FULL
  • OutboxCleanupJob · @Scheduled cron
Tech debt
  • Time-based retention risks loss if Debezium lags > window
  • No HTTP-layer idempotency key — client retries become duplicate orders
  • Same payload DTO for Created/Paid/Cancelled
Hard problem

Get an outbox INSERT out of Postgres and onto Kafka as a clean business event, in commit order per aggregate, without emitting the cleanup DELETEs, without stalling the replication slot.

What we protect
  • Clean wire format — no Debezium envelope leaks to consumers
  • Per-aggregate ordering via aggregate_id as Kafka key
  • The replication slot — advance it even when idle
Solution shape

PostgresConnector + pgoutput. Outbox Event Router SMT extracts payload as the value, routes to outbox.event.${aggregate_type}, and puts the row UUID in the id header. Heartbeats every 10s.

Key tech
  • io.debezium.transforms.outbox.EventRouter
  • route.by.field=aggregate_type
  • table.expand.json.payload=true
  • tombstones.on.delete=false
  • heartbeat.interval.ms=10000
Tech debt
  • tasks.max=1 — Postgres connector is single-task by design
  • JSON on the wire — no Schema Registry
  • snapshot.mode=no_data assumes empty outbox at first launch
  • PoC broker is single-node; Connect internal topics unreplicated
Hard problem

At-least-once delivery + rebalances + manual replay means the same event can arrive twice. Poison messages must not stall the partition. Multiple instances race on the same event id.

What we protect
  • Exactly-once side effect per event_id
  • Bounded blast radius for poison messages
  • Auditability: skipped and dead-lettered records are visible
Solution shape

@KafkaListener MANUAL_IMMEDIATE. Handler is @Transactional: existsById fast-path, then PK insert into processed_events, then side effect. Errors retry with exponential backoff, then DLT.

Key tech
  • ErrorHandlingDeserializer around JsonDeserializer
  • DefaultErrorHandler + ExponentialBackOff(1s, 2.0)
  • DeadLetterPublishingRecoverer
  • processed_events (PK = eventId)
  • Persistable<UUID> skips SELECT-before-INSERT
Tech debt
  • processed_events grows unboundedly — needs TTL
  • Rebalance races produce a confusing DIVEx stack per collision
  • Retry policy is time-bounded, not attempt-bounded
  • Side effect is a log line — real dispatch has its own idempotency story

Shared platform (what ties the three together)

The id header

Outbox row UUID → WAL → SMT → Kafka header → consumer PK. One opaque value, five hands, exactly-once effect.

The aggregate_id key

DB column → SMT → Kafka message key → default partitioner. Per-order commit order for free.

Two databases

cdc (source) holds orders + outbox_events. notifications (consumer) holds processed_events. Same cluster, separate logical DBs.

Absence of KafkaTemplate in the producer

Deliberate. If the producer JVM never sees the broker, "forgot to publish" is impossible.

Replication slot

debezium_order_outbox is the checkpoint. Heartbeats keep it advancing. Losing it re-plays or skips depending on snapshot.mode.

Metrics

Both services expose /actuator/prometheus. Consumer lag + WAL slot lag are the two dashboard-must-haves.

Scaling to a fleet — how each tier changes

Producer · trivial

N pods behind a load balancer. Shared Postgres. Cleanup job needs a lock so it runs once (advisory lock or ShedLock).

No leader election, no cluster membership. HPA on HTTP RPS.

Debezium · HA, not scale

Kafka Connect distributed mode with 2–3 workers. Only one holds the single task at a time; the DB refuses a second attach on the slot.

Never raise tasks.max above 1. Replicate the Connect config/offset/status topics.

Consumer · partitions

N pods in one consumer group. Kafka assigns partitions round-robin; ceiling is the topic's partition count. Shared dedup ledger.

HPA on consumer lag via KEDA. Cap replicas at partition count. Cooperative rebalance for graceful deploys.

The single most operationally sensitive metric: pg_replication_slots.confirmed_flush_lsn vs. pg_current_wal_lsn(). If that gap grows unboundedly, the source DB is on the way to a disk-full outage — regardless of how healthy the rest of the pipeline looks. Detail in CONSISTENCY.md.

Tech debt at a glance

  • Single Kafka broker in the compose file — real deployments need replicated topics for outbox and the Debezium internal topics.
  • JSON on the wire, no schema — a producer field rename silently breaks consumers.
  • REPLICA IDENTITY FULL — heavier WAL writes; fine for outbox, avoid on hot business tables.
  • Time-based outbox retention — must be shorter than max Debezium lag or events are lost.
  • No HTTP-layer idempotency key — client retries create duplicate orders.
  • processed_events grows forever — same TTL problem as the outbox, on the consumer side.
  • Retry policy time-bounded — a 45s DB blip may exhaust retries and DLT a legitimate message.
  • Config lives in three places — application.yml, container env, and outbox-connector.json.
