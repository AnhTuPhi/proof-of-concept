The dual-write problem & the transactional outbox

Module 06. You must change the DB and publish an event. Do them as two independent operations and one can fail alone — a ghost event or a lost event. The outbox makes them one atomic write.

✗ Naïve dual write

Two separate operations. No atomicity.

✓ Transactional outbox

DB row + outbox row in one transaction. A poller ships it later with SKIP LOCKED.

Key insight: the poller marking a row published_at only after the broker ack means a publish failure is retried, never lost. Idempotent producer + event-id header dedupes the rare double-send.
