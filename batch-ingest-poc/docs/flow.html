The three source shapes, side by side

Hard problem

Millions of rows across many files; a single file may exceed heap. Restart must resume mid-file.

What we protect
  • No duplicates in transactions
  • Every rejected row lands in ingest_errors
  • Row count is deterministic across restarts
Solution shape

FilePartitioner round-robins files across grid-size workers. Each worker wraps MultiResourceItemReader around a streaming FlatFileItemReader.

Key tech
  • Reader: MultiResourceItemReader + FlatFileItemReader
  • Partition: FilePartitioner
  • Restart: file index + line offset in ExecutionContext
  • Skip: NumberFormatException, DateTimeParseException, ConstraintViolationException
Tech debt
  • Round-robin skews on mixed-size files
  • Header check is trust-only (linesToSkip=1)
  • No encoding fallback (UTF-8 only)
Hard problem

Columnar format; no cheap "seek to row N." Restart granularity is coarser than CSV; a resume physically re-reads and discards rows.

What we protect
  • Deterministic row count across restarts
  • No file-handle leaks across partitions
Solution shape

Custom ParquetTransactionItemReader implements ItemStreamReader. Persists parquet.fileIndex and parquet.rowIndex; on open(), fast-forwards by discarding rows.

Key tech
  • Reader: AvroParquetReader + custom stream reader
  • Partition: same FilePartitioner as CSV
  • Restart state: file-index + row-in-file
  • Skip: adds IllegalArgumentException (Avro type mismatch)
Tech debt
  • Fast-forward is O(rows-already-read) — not row-group aware
  • Schema is not validated up-front
  • Only two timestamp encodings handled
Hard problem

Live source table; can't hold one long transaction; two workers must never claim the same row.

What we protect
  • Every source row read by exactly one worker
  • Cursor is per-page, not per-partition
  • Idempotent target write
Solution shape

IdRangePartitioner reads MIN(id)/MAX(id) and splits into equal buckets. Each worker's JdbcPagingItemReader filters WHERE id BETWEEN :minId AND :maxId ORDER BY id.

Key tech
  • Reader: JdbcPagingItemReader + PostgresPagingQueryProvider
  • Partition: IdRangePartitioner (disjoint by construction)
  • Restart: page cursor persisted per partition
  • Cursor: opens new statement per page
Tech debt
  • Skewed / sparse id space unbalances partitions
  • No source-side snapshot — new rows during run may be missed
  • Postgres-specific query provider

Shared platform (why adding a fourth source is cheap)

Writer

JdbcBatchItemWriter with INSERT … ON CONFLICT (transaction_id) DO NOTHING. Same instance used by all three jobs.

assertUpdates=false allows the legitimate zero-row updates on duplicates.

Processor

Jakarta Bean Validation runs on every TransactionRecord. Violation → skip + audit row.

Listeners

RejectedItemListener → ingest_errors (job name, step, partition, payload, error class, message).

JobMetricsListener → Micrometer: batch_job_duration, records read/written/skipped.

Infrastructure

BatchInfrastructureConfig publishes the async JobLauncher, JobOperator, a bounded partitionTaskExecutor, and the JobRegistry.

REST surface

POST /jobs/{name}, POST /jobs/{id}/stop, POST /jobs/{id}/restart, GET /jobs/executions/{id}.

JobRepository

Postgres via Spring Batch metadata schema (Flyway V2). All coordination — restart, stop, status — routes through here.

Sub-problem → answer

Sub-problemHow the POC answers it
Volume vs memoryStreaming readers + chunk-size caps the in-flight buffer. No List-of-everything.
Wall-clock latencyPartitioned fan-out on partitionTaskExecutor; disjoint partitions never contend for the same source rows.
Restart after crashReader state (file index / row index / page cursor) persisted in BATCH_STEP_EXECUTION_CONTEXT; each partition resumes independently.
DuplicatesUNIQUE (transaction_id) + ON CONFLICT DO NOTHING. Safe against replayed sources and replayed chunks.
Bad rowsFault-tolerant step with typed skip() list and skipLimit; every skip audited to ingest_errors.
Three source shapes, one pipelineOnly the partitioner and reader change per source. Processor, writer, listeners, skip policy, metrics — all shared beans.
ObservabilityMicrometer timers/counters per job, scraped by Prometheus. Live per-step status via GET /jobs/executions/{id}.
Operator controlSimpleJobOperator exposes cooperative stop + restart; both work across pod restarts because state is in Postgres.

Scaling to a fleet — the three shapes

Shape 1 · Leader-elected

N pods, one leader runs jobs (K8s lease or Postgres advisory lock). Followers serve status & health.

Zero code change. Failover = leader change. Bounded by one pod's CPU.

Shape 2 · Active/active, shared JobRepository

Any pod can launch. Add an app-level "one running per job name" guard using JobExplorer + advisory lock.

Concurrency scales across different jobs; a single job still runs on one pod.

Shape 3 · Remote partitioning

Swap TaskExecutorPartitionHandler → MessageChannelPartitionHandler over Kafka/Rabbit. Workers run on any pod.

Highest throughput. Broker + shared JobRepository become critical infrastructure.

The invariant that ties them all together: the shared Spring Batch metadata schema in Postgres is the single source of truth for what work exists, who owns each partition, and where every worker resumes. Idempotent writes make the ugliest races non-fatal. Detail in CONSISTENCY.md.

Tech debt at a glance

  • Single-JVM partitioning only — remote partitioning is documented, not wired.
  • No auth on /jobs/* — gate with Spring Security before exposing.
  • ON CONFLICT is Postgres-only — port to MERGE for Oracle/SQL Server.
  • ingest_errors grows unboundedly — no TTL, no rollup, no re-drive.
  • Parquet restart is O(rows-already-read) — not row-group aware.
  • DB partitioner assumes dense ids — sparse/skewed key space unbalances workers.
  • Cross-row validation not possible — Bean Validation is per-item; stateful checks need a different stage.
  • Skip listener writes 1 row per skip in its own tx — high skip volume dominates writer time.
