What's hard

  • Stateful compute over an unbounded stream
  • Late & out-of-order events
  • Reference-data joins without shuffles
  • State surviving restarts
  • One bad record can't stall a partition

What we're protecting

  • Throughput on the order path
  • Correctness of derived aggregates
  • Bounded state / memory
  • Availability during rebalance
  • End-to-end latency signal integrity

Key tech

  • GlobalKTable for broadcast reference data
  • JoinWindows + grace period
  • SessionWindows + merger
  • DLQ deserialization handler
  • Interactive Queries (single-instance)
  • REPLACE_THREAD uncaught handler

POC 2 — Windowed Aggregations

Three window semantics over the enriched-orders stream. Every one uses event time with a bounded grace period.

Grace periods — why they matter

A tumbling window "closes" at wall-clock, but our clock is event time. Grace period GRACE_PERIOD = 10s (see WindowedAggregationsTopology.java:41) says: after the window's end timestamp, keep accepting late records for 10 more seconds before locking the aggregate.

Too small → correct records get dropped. Too large → state store grows and downstream sees updates way after the fact. 10s is a decent default when producers stamp reasonable timestamps and clocks are within a few seconds.

Session merger — the subtle bit

When a late event lands in the gap between two existing sessions, Kafka Streams merges them into one. We supply that merger explicitly: 

(key, left, right) -> new UserOrderStats(
    key,
    left.orderCount() + right.orderCount(),
    left.totalSpent().add(right.totalSpent()),
    0L, 0L
)

The merger runs during aggregation, not at emit — so downstream sees the merged session as if it always was one.

Tech debt

  • semantics inner-join — unpaid orders never surface in completed-orders.v1
  • idempotency no dedup on payment side; downstream is on the hook
  • cost selectKey creates a repartition topic — at 10k/s that's real broker traffic
  • clocks trusts producer timestamps; a broken clock breaks the join

Safety net — what keeps the app alive

These aren't POCs. They're what makes the POCs safe to run overnight.

poison pill DLQ handler

DlqDeserializationExceptionHandler catches any deserialization failure, wraps the raw bytes with origin headers (dlq.origin.topic, partition, offset, error.class, error.message), publishes to streams.dlq.v1, and returns CONTINUE so the stream thread doesn't die.

If publishing to the DLQ itself fails, we return FAIL — silent loss is worse than a crash.

produce error Production handler

LoggingProductionExceptionHandler drops only RecordTooLargeException (a known-bad single record). Everything else fails fast — we do not want to silently lose data because of a transient broker problem.

thread crash Uncaught handler

REPLACE_THREAD: a random NPE inside a processor spawns a fresh stream thread instead of leaving the app to bleed threads until it's silently dead. Truly fatal exceptions (broker gone, auth revoked) still propagate so the supervisor can restart.

observability Actuator + Prometheus

/actuator/health, /actuator/prometheus, /actuator/kafkastreams. Kafka Streams JMX metrics are exported as Prometheus timeseries via the Micrometer bridge — thread state, RocksDB stats, and consumer lag are all available on the scrape endpoint.

Scale & consistency

Summary of CONSISTENCY.md. Read the full doc before touching prod.

The unit of scale is the partition, not the pod

Max useful parallelism = partition count. Adding a 4th pod to a 3-partition topic gives you an idle pod. Raise partitions before raising replicas.

What happens when you scale 1 → 2 pods

  1. Second pod joins the consumer group.
  2. Broker rebalances. Some partitions move to the new pod.
  3. Reassigned partitions rebuild state stores from the changelog topic on the new pod.
  4. During rebuild, IQ calls for those keys return InvalidStateStoreException.
  5. After rebuild, keys owned by pod B return 404 on pod A because we don't route.

Consistency by processing.guarantee

ModeGuaranteeCostWhen
at_least_once default Every record processed ≥1 time; duplicates possible under failure Cheap Downstream consumers are idempotent (search indexes, aggregate stores)
exactly_once_v2 Atomic write-output + commit-input via transactions Higher latency, more broker load, tx state RF ≥ 3 Downstream is not idempotent (ledgers, wallets)

Interactive queries under N > 1

Today /api/state/* only works when it hits the pod that owns the key's partition. Fix path:

  1. Set StreamsConfig.APPLICATION_SERVER_CONFIG per pod (POD_IP:8080).
  2. Look up the owning host with KafkaStreams.queryMetadataForKey.
  3. Forward via WebClient with a loop-guard header.
  4. For windowed / range queries, fan out to all instances and stitch.

Pre-flight checklist for N > 1

  • Raise input-topic partition count
  • Set application.server, implement IQ routing
  • Set group.instance.id (static membership)
  • StatefulSet + PVC for state.dir
  • Set num.standby.replicas ≥ 1
  • Add preStop streams-close hook + adequate terminationGracePeriodSeconds
  • Pick EOS vs at-least-once based on downstream idempotency, not vibes
